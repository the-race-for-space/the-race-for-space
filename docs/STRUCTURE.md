# Prototype Structure

This scaffold mirrors the current design direction for **The Race for Space** without committing to gameplay implementation yet.

## Source modules

- `Core/` — mod lifecycle, shared state and cross-module coordination. `RaceRuntime` owns the current race controller, advances race/funding progression on the controlled five-second refresh cadence, requests the heavier player vessel observation path on a separate twenty-second cadence, and samples only the active loaded vessel once per second for starter-contract flight tracking. A newly recorded starter achievement is fed back through the controller's existing non-vessel refresh so line progression, Probe Orbit unlocking, rivals, and projected funding remain centralized. The runtime exposes the tracker read-only for UI presentation; UI code never advances it.
- `Programs/` — player and rival space-program models/state. Rival mission gameplay identity uses stable `NextMissionTargetId`; `NextMissionDisplayName` is presentation-only text derived from the live target catalogues.
- `Tracking/` — KSP-independent vessel classification, body-presence tracking, and starter-flight evaluation from project-owned snapshots. Probe/Relay counts are maintained for observed celestial bodies independently of milestone definitions. Orbital milestone recording evaluates each definition's `UnlockRule` against the full race-program collection at the vessel observation time. `StarterFlightTracker` maintains one player launch attempt, including peak speed/altitude, launch position, latest active-vessel values, continuous Control hold time, orbit disqualification, staging continuity, and one completion per starter line per launch. Directed Power completes only after a qualifying Kerbin surface impact; Mass combines remaining vessel mass with great-circle distance from the launch position; Control requires a continuous crewed altitude hold followed by a crewed Kerbin landing; Biome uses the active Kerbin biome. Current starter-line lookup is shared by gameplay and presentation so rivals can globally unlock the next level without creating conflicting UI state.
- `Milestones/` — achievement/goal definitions and evaluation. `PrototypeMilestones` keeps the normal orbital catalogue separate from the twenty special starter contracts. Starter definitions carry their line, level, reward, rival progress cost, and fixed measurable criteria, while normal orbital definitions keep their body/situation/crew requirements. Flexible unlock definitions use immutable OR-of-AND rules with achievement scope/count, universal-time, and collective satellite-count conditions. `UnlockRuleEvaluator` is the single KSP-independent interpretation of those rules for milestone tracking, funding unlock state, sponsor-offer eligibility, starter-line progression, and read-only UI condition progress.
- `Competition/` — first-to-achieve and comparative-coverage race logic. `SatelliteRaceController` consumes programme collections, does not construct or expose individual funding targets, and caches per-programme projected payouts when its controlled refresh evaluates funding. The runtime can skip the player vessel-observation block on intermediate five-second refreshes while funding, rivals and persistence continue normally. The controller owns the existing funding-day sponsor review for normal achievements and satellite targets: at most two unfinished normal achievement offers and two never-fulfilled satellite offers occupy those random-review slots. The four starter lines are deliberately outside that cap; their next unlocked milestone is offered immediately, and Probe Orbit is offered immediately once any starter line reaches level five.
- `Funding/` — nation/corporation sponsors, offers and awards. `PrototypeFundingCatalogue` owns the code-defined achievement and satellite-network target set. The twenty starter milestones use explicit level rewards of 10k/20k/30k/40k/50k and reuse the normal ten-payment 100% through 10% declining-interest lifecycle. Normal orbital rewards, satellite requirements and network values continue to come from body-tier settings. Probe Orbit is no longer an opening offer: Directed Power V, Mass V, Control V, or Biome V may unlock it. Crewed Orbit still requires any agency to achieve Probe Orbit and then follows the normal sponsor-review flow.
- `Simulation/` — lightweight rival-program simulation for prototype use. Rival progression consumes program and target collections, stable mission target IDs are authoritative, and only programmes already marked Offered are valid mission targets. Starter milestones advance by 20% on each successful rival progress check and use explicit 4k/6k/8k/10k/12k costs for Levels I-V. Five successful starter checks therefore retain the previous total development costs of 20k/30k/40k/50k/60k, while normal orbital and satellite missions continue to advance in 10% steps at their existing costs. Completing a starter objective never creates a satellite; only an actual uncrewed orbital milestone does. Completed one-off objectives remain selectable by rivals that have not personally achieved them until the contract expires; satellite programmes remain repeatable after being offered.
- `Scoring/` — progress/coverage calculations kept separate from funding rules.
- `Persistence/` — save-state models for Race for Space values that must survive KSP save/load cycles. Rival programs remain keyed by stable program ID and race progression persists the next funding time, achievements, programme lifecycle, offers, and satellite-target latches. `StarterFlightSaveState` separately persists the one active pre-orbit flight attempt so peak Directed Power state and partial Control hold time survive normal saves. Older saves without `STARTER_FLIGHT` safely resume with no active attempt. Malformed active-flight nodes fail closed rather than substituting zero values that could erase an altitude violation or invent Control progress; latest live telemetry is reconstructed from the next active-vessel observation instead of being persisted.
- `KspIntegration/` — KSP API adapters, game events, ScenarioModule persistence hooks, vessel discovery, configuration loading, and stable celestial-body presentation ordering. `KspVesselDiscovery` keeps the existing twenty-second loaded/unloaded orbital scan and adds a lightweight active-vessel snapshot for starter contracts containing situation, altitude, surface speed, mass, latitude/longitude, body radius, biome, crew, and launch time. It also converts the active vessel's just-before-destruction callback into a narrow near-surface impact signal consumed by Tracking. Raw KSP vessel objects never enter the starter evaluator.
- `UI/` — race/funding presentation, Command Center visibility, and stock launcher interaction. UI code reads race state but does not own or advance gameplay progression. The Space Race tab now begins with a dedicated four-card `Starter Programmes` panel for Directed Power, Mass, Control, and Biome. Each card shows player line progress, the current globally unlocked target, its 100% reward, and live active-flight progress where relevant. Probe Orbit unlock state is shown above the cards. The twenty starter milestones are omitted from the normal Space Race funding catalogue to avoid duplicate progression presentation, while `Funding Targets` continues to show offered/paying starter contracts so their declining payout lifecycle remains visible. Overview likewise shows only the current starter objective from each line rather than every earlier starter contract that is still paying. Normal Space Race Offered/Unlocked/Locked/Expired sections and satellite/orbital funding presentation remain unchanged.
- `Debug/` — prototype diagnostics and developer-only helpers.

## Distribution layout

`GameData/TheRaceForSpace/` is the installable KSP package layout. `Plugins/` holds the compiled assembly, `Config/RaceSettings.cfg` exposes user-editable campaign balance defaults, while `Assets/` and `Localization/` remain placeholders. Config changes are read when KSP starts and do not add an in-game settings UI.

## Tests

- `tests/TheRaceForSpace.Tests/` mirrors logic-heavy modules so milestone, simulation, tracking, funding, configuration-backed defaults, and persistence rules can be tested without requiring a live KSP scene. The executable test runner explicitly invokes the starter-flight regression suite. Those regressions cover Directed Power impact/ceiling rules and persisted disqualification, Mass distance and one-level-per-launch behavior, Control hold/landing and save/load continuation, Biome progression, staging continuity, live progress values, global rival-driven line unlocking, malformed active-attempt persistence, and the starter-specific 20% rival progress pacing with unchanged total development costs.
- `tests/TheRaceForSpace.ControllerTests/` compiles the real `SatelliteRaceController` against small test-only stand-ins for its existing KSP integration boundaries. It covers cross-module controller ordering without adding test seams to production code or requiring a KSP installation, including special starter offers and the four-way Probe Orbit convergence alongside the existing funding/rival regressions.
- `tools/run-logic-tests.sh` runs both standalone suites.
- `.github/workflows/logic-tests.yml` runs the same script on Ubuntu with .NET 8 for pushes and pull requests.
- `docs/KERBAL_CONTRACTS_V0_5_TESTING.md` records the required live-KSP acceptance pass for callbacks, biome reporting, active-vessel telemetry, UI layout, save/load behavior, and the end-to-end four-line-to-Probe-Orbit flow.

Live KSP API behavior such as active-vessel destruction callbacks, stock biome reporting, loaded/unloaded vessel discovery, actual Career-funds integration, direct `RaceSettings.cfg` loading, and Command Center layout still requires in-game verification.

## Prototype rule

Keep the first implementation narrow: normalize KSP state at the integration boundary, keep mission rules deterministic and testable outside KSP, avoid per-frame scans, persist only project-owned state that cannot be reconstructed safely, and reuse the existing funding/rival/unlock flow instead of creating parallel gameplay systems.
