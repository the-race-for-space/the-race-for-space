# Prototype Structure

This scaffold mirrors the current design direction for **The Race for Space** without committing to gameplay implementation yet.

## Source modules

- `Core/` — mod lifecycle, shared state and cross-module coordination. `RaceRuntime` owns the current race controller, advances race/funding progression on the controlled five-second refresh cadence, and requests the heavier player vessel observation path on a separate twenty-second cadence independently of the UI. `RaceSettings` holds the KSP-independent campaign balance values loaded once before controller creation, including body-tier rewards/costs, funding interval and rival defaults.
- `Programs/` — player and rival space-program models/state. Rival mission gameplay identity uses stable `NextMissionTargetId`; `NextMissionDisplayName` is presentation-only text derived from the live target catalogues.
- `Tracking/` — KSP-independent vessel classification and body-presence tracking from project-owned vessel snapshots. Probe/Relay counts are maintained for observed celestial bodies independently of milestone definitions. Milestone recording evaluates each definition's `UnlockRule` against the full race-program collection at the vessel observation time, repeating when a new player achievement can satisfy another rule in the same snapshot.
- `Milestones/` — achievement/goal definitions and evaluation. `PrototypeMilestones` is the code-defined catalogue of current prototype achievement targets. Flexible unlock definitions use immutable OR-of-AND rules with achievement scope/count, universal-time, and collective satellite-count conditions. `UnlockRuleEvaluator` is the single KSP-independent interpretation of those rules for milestone tracking, funding unlock state, sponsor-offer eligibility, and read-only UI condition progress. Satellite-count conditions sum the project-owned qualifying satellite counts across all race programs; they do not invent historical per-satellite timestamps.
- `Competition/` — first-to-achieve and comparative-coverage race logic. `SatelliteRaceController` consumes programme collections, does not construct or expose individual funding targets, and caches per-programme projected payouts when its controlled refresh evaluates funding. The runtime can skip the player vessel-observation block on intermediate five-second refreshes while funding, rivals and persistence continue normally. Unlock rules are evaluated at explicit current, vessel-observation, projected-funding, or historical funding-boundary times as appropriate. The controller also owns sponsor reviews: at each processed funding boundary, existing Offered contracts pay first, then unlocked candidates are randomly selected into vacancies for the next period. At most two unfinished achievement offers and two never-fulfilled satellite offers occupy slots; vacancy counts are snapshotted once per review so a newly offered pre-completed target cannot cascade into extra same-day offers. Normal refreshes may unlock targets or free slots but never refill them. Rival count, starting funds and the shared funding interval come from `RaceSettings`; Aster and Cobalt retain their stable identities while additional configured rivals use numbered stable IDs.
- `Funding/` — nation/corporation sponsors, offers and awards. `PrototypeFundingCatalogue` owns the code-defined achievement and satellite-network target set, while rewards, satellite requirements and network values come from the current body-tier settings. Achievement and satellite programmes store `UnlockRuleDefinition`; availability itself is evaluated outside Funding by the shared milestone evaluator. Satellite-network progression gates use 60% of the configured prerequisite network size: Mun/Minmus require Kerbin Probe Orbit plus Kerbin network progress, interplanetary planets require their Probe Orbit plus Mun and Minmus network progress, and planetary moons require their Probe Orbit plus parent-planet network progress. Programme state records whether a sponsor has offered the contract; satellite programmes separately latch whether their full network target has ever been reached. Only Offered programmes are eligible for controller payouts or rival mission selection. Probe Orbit and Crewed Orbit remain the two opening achievement offers for a fresh campaign.
- `Simulation/` — lightweight rival-program simulation for prototype use. Rival progression consumes program and target collections, stable mission target IDs are authoritative, and only programmes already marked Offered are valid mission targets. Unlock-rule evaluation and sponsor selection remain controller responsibilities. Completed one-off objectives remain selectable by rivals that have not personally achieved them until the contract expires; satellite programmes remain repeatable after being offered. Display names are presentation only. Rival 10% progress costs and progress chance come from `RaceSettings`; mission cadence and target-selection behaviour otherwise remain fixed prototype rules.
- `Scoring/` — progress/coverage calculations kept separate from funding rules.
- `Persistence/` — simple save-state models for Race for Space values that must survive KSP save/load cycles. Rival programs are persisted as a collection keyed by stable program ID, with stable mission target IDs rather than presentation-name migration. Race progression persists the next shared funding universal time, satellite unlock state, achievement-contract lifecycle, sponsor-offer state, and the satellite full-target latch. Older funding nodes without offer fields restore previously unlocked satellite funding as already offered; older started achievement contracts remain offered, while missing target-reached history safely defaults false.
- `KspIntegration/` — KSP API adapters, game events, ScenarioModule persistence hooks, vessel discovery, configuration loading, and stable celestial-body presentation ordering. `RaceSettingsLoader` reads `GameData/TheRaceForSpace/Config/RaceSettings.cfg` once before the first race controller is created and keeps built-in defaults for missing or invalid values. `KspVesselDiscovery` resolves loaded and unloaded KSP vessel state into project-owned tracking snapshots when requested by the twenty-second player observation schedule before tracking rules consume it. Space Race funding presentation can request a Kerbin-relative orbital-distance sort key without hardcoding individual body names in the UI.
- `UI/` — race/funding presentation, Command Center visibility, and stock launcher interaction. UI code reads race state but does not own or advance gameplay progression. Space Race exposes four collapsible funding-state sections in sponsor lifecycle order: `Offered`, `Unlocked`, `Locked`, and `Expired`; Offered is expanded by default while the other sections start collapsed. Unlocked targets state that their requirements are met and they are waiting for a future funding review, while Locked targets continue to show live achievement, time, and collective satellite-network requirements from the shared evaluator. Funding Targets shows only Offered, non-expired achievement contracts and Offered satellite programmes, including completed/paying achievements and previously fulfilled satellite networks; Unlocked funding is omitted. Overview's `Your Objectives` list is likewise limited to Offered, non-expired achievement contracts so it cannot contradict Space Race, while the rest of Overview and Rival Agencies remain unchanged. Funding buttons remain four per row and are sorted from Kerbin outward using each objective's existing celestial-body data. A small `?` button continues to open the unchanged in-game Help / Player Guide. Recurring IMGUI scratch buffers, layout options, and the window callback are reused rather than recreated for every draw event.
- `Debug/` — prototype diagnostics and developer-only helpers.

## Distribution layout

`GameData/TheRaceForSpace/` is the installable KSP package layout. `Plugins/` holds the compiled assembly, `Config/RaceSettings.cfg` exposes user-editable campaign balance defaults, while `Assets/` and `Localization/` remain placeholders. Config changes are read when KSP starts and do not add an in-game settings UI.

## Tests

- `tests/TheRaceForSpace.Tests/` mirrors logic-heavy modules so milestone, simulation, tracking, funding, configuration-backed defaults, and persistence rules can be tested without requiring a live KSP scene. It compiles both the unlock definition model and evaluator and includes consumer-level tracking/rival regressions, catalogue checks for the satellite-network progression graph, opening-offer checks, and offer/fulfilment persistence migration coverage.
- `tests/TheRaceForSpace.ControllerTests/` compiles the real `SatelliteRaceController` against small test-only stand-ins for its existing KSP integration boundaries. It covers cross-module controller ordering without adding test seams to production code or requiring a KSP installation. The runner also hosts focused unlock-rule evaluator, offered-rival-target, collective satellite-count, configured-rival-count, configured-funding-interval, scheduled-vessel-observation, overdue-funding-boundary, sponsor-review timing, offer-cap, no-cascade, and historical multi-boundary regressions.
- `tools/run-logic-tests.sh` runs both standalone suites.
- `.github/workflows/logic-tests.yml` runs the same script on Ubuntu with .NET 8 for pushes and pull requests.

Live KSP API behavior such as loaded/unloaded vessel discovery, actual Career-funds integration, direct `RaceSettings.cfg` loading, and Command Center layout still requires the documented in-game verification path.

## Prototype rule

Keep the first implementation narrow: prove we can read persistent/unloaded vessel data, classify vessel presence around/on celestial bodies, maintain per-program state, evaluate a small milestone set, and award a simple funding outcome. Rival simulation, UI polish and richer sponsor behaviour should remain replaceable layers.
